## FIX
1. **Double fire of a ready job (duplicate analysis and report).** `fireReady` has no claim. In `/api/mac/bundle` the job is written `state:"ready"` and `fireReady` then awaits `fireRoutine` (a network call, seconds) before deleting the row. Every Telegram webhook (and every Mac poll) runs `sweep()` first, which lists the same `ready` row and calls `fireReady` again: a second rate slot, a second routine fire, a second report. The same race exists any time a job sits `ready` because the rate cap was full and a webhook and a poll sweep at once. Fix: claim before firing, e.g. `kv.atomic().check(entry).delete(key).commit()` and only fire if `ok`; the existing user message on fire failure already covers the "lost" case. Add a deno test with a webhook arriving during the fire.
2. **`/api/defer` is an unbounded queue/spam and fetch-anything path for anyone who holds `RELAY_SECRET`** (in practice a prompt-injected routine, which reads hostile video/repo text). It checks only that `chat_id` is the owner's, not that the update was real: any `update_id`, any `text` (so any public URL the Mac then fetches with yt-dlp, up to 200 MB, two attempts), no cap on queued jobs, and each defer sends a Telegram message to the owner. `sweep()` also lists every job on every webhook. Cheapest fix: require the `["upd", update_id]` row the webhook already writes to exist (the job must come from a real owner message) and cap pending Mac jobs (say 5, reply `queued:false` beyond it).
3. **`relay_url` in `/api/defer` is taken from the caller and not length-capped** (`typeof j.relay_url === "string" ? j.relay_url : ""`). It is stored and later re-sent in the routine fire; the routine then builds `Relay(job.relay_url)` and sends `RELAY_SECRET` there (`check_relay_url` only requires plain https, not same-origin). A caller can point a queued job's `relay_url` at another host, and an oversized string also makes the KV write throw (>64 KiB). The relay already knows its own origin (`ownerMessage` sets `relay_url: origin`): use that and ignore the body field.

## FIX (functional, not security) — local Whisper never runs
`mac_worker.handle` calls `transcribe(work)` with the **temp directory**, but `local_only_transcript(video)` does `WhisperModel(...).transcribe(str(video))`. A directory raises, the broad `except` returns `""`, and the user silently gets no transcript for any video without captions (the report only says "No captions were available"). Pass the media file (`find_media(work)` from `reelay.cloud.speech`). Tests use a fake `transcribe`, so none covers this; add one with a real temp folder and a stub model. Also wrap the model call in a time limit: it is the one step with no timeout, and a hung Whisper holds the one-shot launchd process, so no further polls run until it is killed.

## Checked and fine, per your priorities
1. **Secrets.** `/api/mac/*` is dispatched before `/api/*`, and `macApi` compares only `MAC_SECRET` (constant-time, 401 if unset). `api()` compares only `RELAY_SECRET`. So neither opens the other's routes, and with either secret unset the routes 401. Errors/logs: relay returns fixed strings; the worker prints only exception type names and `relay answered N for METHOD path`; `mac_secret` is only in the Authorization header, not in the plist, log or output. Worker uses `_NoRedirect` and https-only `relay_url`.
2. **Mac safety.** The worker has no model call; Groq is off (`use_whisper=False`, local Whisper `local_files_only=True`); yt-dlp runs with `--ignore-config`, `--` before the URL, no cookies/proxy/TLS flags, `http(s)` only (no `file:`), `is_private_host` pre-check, `--max-filesize 200M`, duration filter. The relay sends only a reason code plus a sanitised host (`[A-Za-z0-9.-]`, 60 chars); user text comes from a fixed table. Temp folder is `mkdtemp` and always removed in `finally`. Known limit (R-8): a redirect to an internal host is not caught; with FIX 2 this needs a compromised routine, so I accept it.
3. **Bundle.** The relay checks strict base64, JPEG magic, ≤50 KB per frame, ≤20 frames, `0 ≤ time_s < 3600`, ≤1.5 MB body, and caps transcript/caption. `prepare` re-validates everything and writes frame files itself (`frame_NNN.jpg` under its own folder; no path from the upload). Magic bytes are only 3 bytes (non-JPEG data after `ffd8ff` passes); acceptable since the frames are just model input and already untrusted. KV: each frame ≤50 KB and meta ≤~54 KB, under the 64 KiB value cap; the worst-case body (20×50 KB base64 + 24k transcript with `\uXXXX` escapes) is ~1.495 MB, just under the 1.5 MB cap; if it were exceeded the relay returns 413 and the user is still told after two attempts.
4. **Nothing vanishes silently.** Lease 15 min, two attempts, then "started twice but never finished"; 24 h expiry message; fail path deletes and tells the user; bundle waiting on a full rate cap stays `ready` and is retried by every sweep. Cron is guarded (`try`, feature check) and the sweep also runs on every webhook and every Mac poll. Gaps (NIT below).
5. **No loops.** `defer` refuses `bundle_id`/`file`, `prepare._defer_to_mac` refuses when `bundle_id` is set, `/fail` and `/bundle` delete or advance the row, retries are lease-based and max 2, yt-dlp retries are 0, one job per 60 s poll. Only an unreported crash causes a second download.
6. **launchd.** Own label `com.reelay.macworker`, `StartInterval 60`, no `KeepAlive`, `RunAtLoad`; `install` boots out/in only its own label; `remove` only its own label and plist; the bot service is not touched. launchd does not start a second copy while one is running.
