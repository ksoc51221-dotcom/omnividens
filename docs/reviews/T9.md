## What a user sees
1. `curl -fsSL <raw url>/installer/install.sh | sh`: installs `uv` if missing (into `~/.local/bin`, no admin), then `uv tool install --with-executables-from yt-dlp git+<repo>`, then `uv tool update-shell`, then runs `reelay setup` reading the keyboard from `/dev/tty` (since stdin is the pipe). uv fetches a suitable Python itself. Refuses to run as root and while the repo URL is still the `REPLACE-ME` placeholder (override with `REELAY_REPO=...`).
2. `reelay setup`, six screens: (1) check ffmpeg+ffprobe / yt-dlp / Claude Code, with the exact fix; offers to run `brew install ffmpeg` or `uv tool install yt-dlp` only on a yes; the Claude Code curl line and Homebrew are only printed, never run. (2) BotFather steps, hidden token input, shape check, `getMe` lookup to get the bot username (offline: type the username). (3) allow-list folders (must exist; `/` and the Home folder refused). (4) optional Anthropic key with the "costs real money, set a spend limit first" warning; must start `sk-ant-`. (5) write `~/.reelay/config.toml` (0600, dir 0700, atomic, old file kept as `config.toml.bak`, unrelated keys preserved). (6) pairing: `https://t.me/<bot>?start=<code>` as QR + link + plain `/start CODE`, then either background service (explicit yes, default no) and waits for "Paired!", or runs the bot in the window.
3. `reelay doctor`: one screen, `OK / FIX / TIP` per item (tools, settings file private, token, folders exist, API key, pairing, starts-at-login), then "what to do next". Exit code 1 only if something required is wrong.
4. `reelay service install | remove`: launchd agent `~/Library/LaunchAgents/com.reelay.bot.plist` (RunAtLoad, restart on crash, log in `~/.reelay/reelay.log`). It stores the PATH of the terminal that ran setup, because launchd's PATH would not find ffmpeg / claude / yt-dlp. Removal stops it and deletes the file.
5. Also: `reelay pair` (new code + QR), `reelay` / `reelay run` (the bot), `reelay --help`.

## Secrets
Read with `getpass` (hidden). Never printed, never in prompts, never in the plist, never in error text (the Telegram helper raises argument-less exceptions with `from None`, since its URL contains the token). Only destination is `api.telegram.org` for the token (the `getMe` call) and the config file. After saving, the wizard drops them from memory. Tests assert this (`test_secrets_never_appear_on_screen_or_in_prompts`, `..._use_hidden_input`, plist and `pair` output checks).

## Design choices
| Choice | Why | Cost |
|---|---|---|
| New package `reelay/installer/` (not `installer/` Python) | a console script needs an importable package; `installer/` holds only `install.sh` | one extra folder |
| Wizard logic takes a `Deps` of fakes | whole flow tested with scripted answers, no network | long `Deps` list |
| Never run remote scripts or Homebrew for the user | safety and the "no admin password" rule | user copies two commands |
| Service default is "no", but we explain both options | brief says only if user says yes | users who say no must keep a window open |
| Hand-written TOML writer | no new dependency | only simple values; unsupported ones abort without touching the file |
| Existing service is restarted without asking | a running bot would not see the new code or token | one extra restart |

## T7 review of agent/t9-netcheck @ f5193b0 (read-only; read netcheck.py and the doctor/wizard diffs; probed with fake openers)
Good: bare-host request with no token, redirects not followed (a 3xx counts as reachable), default certificate verification and no way to turn it off, injectable opener, the wizard saves settings before the network gate and exits 1 with clear next steps. No BLOCKER.
- **FIX `check_telegram` can still raise.** Only `OSError`/`URLError`/`HTTPError` are caught. A filter that answers with garbage makes `http.client.BadStatusLine` / `IncompleteRead` (both `HTTPException`, not `OSError`) and a weird hostname gives `UnicodeError`; I verified both propagate out of `check_telegram`, which would crash `reelay doctor` and `reelay setup` at the very moment the network is flaky. Add a final `except Exception` → "connection failed" (and a test with `BadStatusLine`).
- **FIX A certificate error is blamed on the network without proof.** The same `CERTIFICATE_VERIFY_FAILED` appears when the Mac's clock is wrong or Python lacks CA certificates, and then every site fails, not only Telegram. Before saying "this network is filtering Telegram", try one neutral HTTPS site too (e.g. `https://example.com/`): if that also fails the cert check, say "your Mac can't verify any HTTPS site: check the date/time and run `/Applications/Python*/Install Certificates.command` or reinstall"; only if the neutral site works is it a Telegram filter. Cheap, and it turns a guess into a diagnosis.
- **NIT** This check uses Python's `urllib` and the system CA bundle, but the bot talks to Telegram through httpx/python-telegram-bot, which uses `certifi`. The two can disagree (a filter's CA may be trusted by one and not the other), so a pass here isn't a guarantee for the bot. Say so in a code comment, and make the real bot's startup error (T8) the source of truth.
- **NIT** DNS blocking (`socket.gaierror`) is another common filter mode; it currently reads "check your internet connection". Mention "or this network may be blocking Telegram" for that case.
- **NIT** `ssl.SSLError` also covers non-certificate failures (handshake reset by a filter); "filtering" is a good guess there too, but the message could say "or something is interfering with secure connections".
- **NIT** `doctor` now waits up to 5 s for this check; print "checking your connection…" first so it doesn't look hung.

Fix the two FIXes and I'd approve.
